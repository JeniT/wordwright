Read this when someone asks to add Gemini (Google) as a second LLM provider, or when you design anything else that must work with more than one provider.

# How do we let people use Gemini instead of Claude? (research)

Question: Wordwright is bring-your-own-key. How would a writer who prefers Gemini use their Gemini key instead of an Anthropic one?

Researched 24 Oct 2026. **No code was changed.** Sources and how far to trust them:

- **Read directly (strongest):** the repo files cited as `path`; Google's published REST description of the Gemini API, fetched on 24 Oct 2026 from `https://generativelanguage.googleapis.com/$discovery/rest?version=v1beta` (revision `20261023`; called "the v1beta reference" below); the `@google/genai` 2.31.0 package from npm (published 2026-10-23), unpacked and read; and **live calls** to Google's API with a made-up key (no real key was used or available).
- **Read through a summarising fetch tool:** the pages on `ai.google.dev`. The tool answers from the page with a small model, so wording is paraphrased and parts of long pages were cut off. Where a page did not say something, I say so rather than fill the gap. Treat page-derived specifics as "per the page" and re-read the page before building on them.
- **Not checked at all** is marked **unverified**. Nothing here was run against a real Gemini key, so every behavioural claim (does replay need thought signatures, what a real error looks like) needs the checks listed at the end.

## Short answer

Gemini can be added the way the repo already intends: one new adapter (`GeminiProvider`) behind the existing `LLMProvider` port, one more for Research (`GeminiResearchProvider`), a new id in `LLM_PROVIDER_IDS`, and a case in each factory. The port was written to be vendor-neutral, and most of it maps cleanly. **Three things are not routine:**

1. **Conversation replay and Gemini's "thought signatures".** The brainstorm thread is stored in our own neutral format with no model reasoning, so it can replay on any provider (`apps/api/src/db/database.ts`). Gemini 3 models return opaque signatures that must be sent back in stateless use, and the API has a finish reason, `MISSING_THOUGHT_SIGNATURE`, for requests that lack one. Whether our tool-call-then-follow-up pattern trips it is unverified and is the first thing to test.
2. **Privacy.** On Gemini's free tier Google uses prompts and replies to improve its products and humans may read them; on paid (billing-enabled) use it does not. A writer cannot tell from the key which they have, and our "protect what you write" advice is Anthropic-specific.
3. **Research.** Google Search grounding exists, but Gemini 3 models do not offer it on the free tier, and whether the addresses it returns are real page addresses (not Google redirect links) was not confirmed for the endpoint we would use. Our Research feature rejects any address not found in the search results, so this decides whether it works.

Owner decisions are listed at the end. Everything in `prompts/` is tuned for Claude; **changing a prompt is a product change and the owner must review it**.

## 2. Gemini against primary sources

### 2.1 Two APIs: `generateContent` and Interactions

Google now has two ways to talk to the Gemini models. This is the biggest design choice and it is new.

- **`generateContent` / `streamGenerateContent`** (`POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent`, and `:streamGenerateContent` with `alt=sse`), described in the v1beta reference.
- **Interactions** (`POST https://generativelanguage.googleapis.com/v1beta/interactions`). Per `https://ai.google.dev/gemini-api/docs/interactions`: "Generally Available and recommended for all new projects"; `generateContent` is "considered legacy" but "remains fully supported"; new models, tools and agentic features will launch on Interactions. It records a conversation as steps (thoughts, `function_call`, `function_result`, `model_output`), can keep history on the server (`previous_interaction_id`, `store` defaults to true) or run stateless (`store: false`). Stored interactions are kept 55 days on paid projects (7, 14, 28 or 55 chosen in AI Studio) and **1 day on the free tier**, per that page. `store: false` cannot be combined with `previous_interaction_id`.
- The v1beta reference I fetched lists no `interactions` resource (its resources are `models`, `files`, `cachedContents`, `batches`, `tunedModels` and similar), so Interactions is documented on the pages and in the SDK but not in that machine-readable description. The 2.31.0 SDK has both (`ai.interactions` and `ai.models`, in `dist/genai.d.ts`).
- Many `ai.google.dev` guides (function calling, structured output, Google Search, URL context, system instructions, tokens) now show only Interactions examples and field names (`system_instruction`, `tool_choice`, `response_format`, `function_result`). The v1beta reference is the authority for `generateContent` field names.

Wordwright's store-nothing-with-the-provider stance (we keep the conversation, replay it each turn) matches **stateless** use of either API. Server-side state (`previous_interaction_id`) would put writers' text in Google's storage for 1 to 55 days and would break replay across providers, so I would not use it.

### 2.2 Auth, key checking, model list

- **Key:** created at `https://aistudio.google.com/apikey`; each key belongs to a Google Cloud project that carries billing and quota (`https://ai.google.dev/gemini-api/docs/api-key`). The page does not state a key prefix (Gemini keys are commonly seen starting `AIza`; **unverified at a primary source**). Per that page, from 28 May 2026 new AI Studio keys are "authorization keys" tied to a service account, "the Gemini API rejects requests from unrestricted standard keys" (keys made in the Cloud console need restricting to the Gemini API), and unrestricted keys long dormant are blocked from 7 May 2026. A writer with a Cloud-console key may hit this; the error text for it is **unverified**.
- **How the key is sent:** the SDK sends header `x-goog-api-key` (`@google/genai` 2.31.0, `dist/index.mjs`); the REST reference's examples use `?key=`. I confirmed live that the header and the query form both work. **Use the header** so keys do not land in URLs or logs.
- **Key validation:** `GET /v1beta/models` is the natural check, as `listModels` already is for Anthropic, and costs no tokens. **Live result with a made-up key (24 Oct 2026): HTTP 400, `status: "INVALID_ARGUMENT"`, message "API key not valid. Please pass a valid API key.", with `details[0].reason = "API_KEY_INVALID"`.** With no key: HTTP 403 `PERMISSION_DENIED`. So an invalid key is a 400, not a 401. This contradicts the errors page, which lists 401 `authentication` for "invalid or expired" keys (`https://ai.google.dev/gemini-api/docs/api-errors`). The adapter must read `error.details[].reason`, not rely on the status code. A real valid key was not available, so a successful list is unverified.
- **Model list:** `models.list` takes only `pageSize` (default 50, at most 1000) and `pageToken`; there is no filter (v1beta reference; `https://ai.google.dev/api/models`). Each `Model` has `name` (`models/gemini-...`, so strip the prefix before use), `baseModelId`, `version`, `displayName`, `description`, `inputTokenLimit`, `outputTokenLimit`, `supportedGenerationMethods`, `thinking`, and sampling defaults. **There is no line, release date or lifecycle on a listed model**, so the Anthropic adapter's "drop deprecated, mark newest per line as `latest`" cannot be copied. The adapter would filter on `supportedGenerationMethods` containing `generateContent` and on `gemini-` in the name (the list also holds embedding, TTS, image, Live and agent models; `https://ai.google.dev/gemini-api/docs/models`) and decide `latest` some other way (see "What it would take"). Stage and retirement time appear only on responses (`modelStatus.modelStage`, `retirementTime` in `GenerateContentResponse`), not in the list. Whether the list omits shut-down models is **unverified**.
- **Versioning:** Stable (pinned), Preview (production use allowed, "at least 2 weeks' notice" of deprecation), Latest (alias hot-swapped on new releases, 2 weeks' notice), Experimental (not for production) (`https://ai.google.dev/gemini-api/docs/models`). The deprecations page gives no fixed notice for stable models (`https://ai.google.dev/gemini-api/docs/deprecations`). On 24 Oct 2026 the models page lists `gemini-4-argon`, `gemini-3.8-flash`, `gemini-3.6-flash` and `gemini-3.5-flash-lite` as stable text models, and says `gemini-2.5-*` access is limited to recent users.

### 2.3 System instructions, roles, messages

- `systemInstruction` is a `Content`, and "Currently, text only" (v1beta reference, `GenerateContentRequest`). Our system prompts are text, so this is fine.
- Roles are `user` and `model`, not `assistant` (`Content.role` in the v1beta reference).
- There is no equivalent of Anthropic's rule that `tool_result` blocks must come first in the user message; **unverified** whether Gemini imposes any ordering (the pages fetched do not say).

### 2.4 Function calling, against our tool use

What differs from Anthropic (v1beta reference schemas `Tool`, `FunctionDeclaration`, `FunctionCall`, `FunctionResponse`, `FunctionCallingConfig`; `https://ai.google.dev/gemini-api/docs/function-calling`):

| Point                  | Anthropic (today)                                  | Gemini                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------------- | -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Declaring a tool       | `input_schema` (JSON Schema object)                | `tools: [{functionDeclarations: [{name, description, parametersJsonSchema}]}]`. `parametersJsonSchema` takes JSON Schema; the older `parameters` field is an OpenAPI 3.0 subset and the two are mutually exclusive. Names: letters, digits, `_ : . -`, up to 128 characters.                                                                                                                                                 |
| Which schema keywords  | Anything                                           | The v1beta reference lists the supported keywords for `responseJsonSchema` (see 2.5). It does not repeat that list for `parametersJsonSchema`; assuming the same subset is **unverified**. The function-calling page says only "a subset of the OpenAPI schema" and that very large or deeply nested schemas may be rejected.                                                                                                |
| Call id                | Always present (`tool_use.id`)                     | `FunctionCall.id` is **optional** ("If populated..."). The adapter has to make up ids when it is missing, and the port's `tool_call.id` is required.                                                                                                                                                                                                                                                                         |
| Answering a call       | `tool_result` with `tool_use_id`, text, `is_error` | `functionResponse` part with **`name` required**, optional `id`, and `response` which must be a JSON **object**. Errors are conventionally `{ "error": ... }`. Our `tool_result` carries only the call id, so the adapter has to look up the tool's name from the earlier `tool_call` in the history.                                                                                                                        |
| Parallel calls         | Several `tool_use` blocks in one reply             | Supported ("can call several independent functions in one turn"); the page does not say how parallel results must be ordered.                                                                                                                                                                                                                                                                                                |
| Stop reason for a call | `tool_use`                                         | **No such finish reason.** The `finishReason` enum (below) has none; the reply ends `STOP` and carries `functionCall` parts. The adapter must infer our `tool_use` from the parts.                                                                                                                                                                                                                                           |
| Forcing / forbidding   | `tool_choice`                                      | `toolConfig.functionCallingConfig.mode`: `AUTO` (default), `ANY`, `NONE`, `VALIDATED`, with `allowedFunctionNames`. We do not use this today.                                                                                                                                                                                                                                                                                |
| Reasoning continuity   | Not required of us (we never replay thinking)      | Parts can carry `thoughtSignature`, "an opaque signature for the thought so it can be reused in subsequent requests". Stateless use must send thought blocks back "unmodified" (`https://ai.google.dev/gemini-api/docs/thinking`). The enum includes `MISSING_THOUGHT_SIGNATURE`: "Request has at least one thought signature missing." **Which models and turns enforce it is not stated on the pages I read: unverified.** |
| Number of tools        | Five for us                                        | No hard limit stated; the page advises about 10 to 20 active tools. Five is fine.                                                                                                                                                                                                                                                                                                                                            |
| Built-in plus custom   | n/a                                                | Gemini 3 models can combine built-in tools (Google Search, URL context) with function calling (function-calling and Google Search pages). Not needed for brainstorm, which is not given search.                                                                                                                                                                                                                              |

Our tool schemas are Zod objects with `.max()`, `.min()`, `.trim()`, a `WebAddressSchema` and one `.default('')` (`packages/core/src/domain.ts`, ~lines 1051 to 1100). These become `minLength`, `maxLength`, possibly `format` and `pattern`, and `default` in the JSON Schema. Per the structured-output page, length keywords are silently stripped, which is harmless because we re-validate every tool input. How `default`, `pattern` and `format: uri` are treated by function declarations is **unverified**; test the five real tool schemas.

### 2.5 Structured output and JSON Schema

- Set `generationConfig.responseMimeType: "application/json"` with a schema. The v1beta reference marks `responseJsonSchema` **Deprecated** in favour of `responseFormat` (`text.mimeType: APPLICATION_JSON`, `text.schema`), and keeps `responseSchema` (an OpenAPI 3.0 subset) as the older route. Interactions uses `response_format` (`https://ai.google.dev/gemini-api/docs/structured-output`).
- Supported JSON Schema keywords (v1beta reference, `GenerationConfig.responseJsonSchema`): `$id`, `$defs`, `$ref`, `$anchor`, `type`, `format`, `title`, `description`, `enum` (strings and numbers), `items`, `prefixItems`, `minItems`, `maxItems`, `minimum`, `maximum`, `anyOf`, `oneOf` (treated as `anyOf`), `properties`, `additionalProperties`, `required`; plus non-standard `propertyOrdering`. Cyclic references only in non-required properties. The structured-output page adds that `minLength`, `maxLength`, `minProperties`, `maxProperties`, `uniqueItems`, `contains` are accepted and **ignored**, and that big or complex schemas can return `400 INVALID_ARGUMENT` (large nested `maxItems`, long names, many enum values, many `anyOf` branches). No numeric limit on schema size is published.
- Zod to this: the page itself uses `z.fromJSONSchema` for validating; Zod's `z.toJSONSchema` output (what `llmTool` uses) should mostly fit, but `pattern`, `default`, `exclusiveMinimum` and string `format: uri` are not on the supported list. **Unverified** whether they cause errors or are dropped.
- Combining structured output with tools: per the page, only Gemini 3 series, and labelled Preview.
- Wordwright does not use provider structured output today, so nothing needs porting. It is a possible later improvement for Critique and Rephrase (fewer 502s on unparseable JSON) but would need a schema field on `LLMRequest`, which is a port change and out of scope for a first Gemini adapter.

### 2.6 Streaming, finish reasons, blocks

- Streaming: `streamGenerateContent` (server-sent events) or `ai.models.generateContentStream()` in the SDK. Whether function calls arrive whole or in pieces in the stream, and which chunk carries `usageMetadata`, is **unverified** (the Interactions page says call arguments arrive as deltas to aggregate; the `generateContent` behaviour was not read).
- `finishReason` values (v1beta reference, `Candidate.finishReason`): `STOP`, `MAX_TOKENS`, `SAFETY`, `RECITATION`, `LANGUAGE`, `OTHER`, `BLOCKLIST`, `PROHIBITED_CONTENT`, `SPII`, `MALFORMED_FUNCTION_CALL`, `UNEXPECTED_TOOL_CALL`, `TOO_MANY_TOOL_CALLS`, `MISSING_THOUGHT_SIGNATURE`, `MALFORMED_RESPONSE`, `ESCALATION`, `PUP_LIMITED_DISABLED`, `CONTINUATION`, and several image ones. `CONTINUATION` means the reply hit a per-request token limit but can be continued with a `continuationToken`.
- A blocked prompt has no candidates and `promptFeedback.blockReason` (`SAFETY`, `OTHER`, `BLOCKLIST`, `PROHIBITED_CONTENT`, `IMAGE_SAFETY`). The safety-settings page says blocked input or output fails with an HTTP 400 error whose code is `safety`, `jailbreak`, `prohibited_content` or `blocklist` (Interactions behaviour per the page), so both a 400 and an empty-candidates reply are possible paths.
- Safety settings: categories `HARASSMENT`, `HATE_SPEECH`, `SEXUALLY_EXPLICIT`, `DANGEROUS_CONTENT`, `JAILBREAK` (and others in the reference) with thresholds from `BLOCK_LOW_AND_ABOVE` to `OFF`. Default is "Off for Gemini 2.5 and later models"; "core harms" are always blocked and cannot be changed (`https://ai.google.dev/gemini-api/docs/safety-settings`). This matters to us: Wordwright's own rule is that the AI gives a short warm reply to a distress disclosure (`prompts/brainstorm-rules.md`; `docs/responsible-ai.md`); a safety block on such a message would be a refusal with no reply, which our `refusal` stop reason already handles ("an empty reply has nothing to replay"). Whether Gemini blocks distress or self-harm disclosures at default settings is **unverified** and should be tried in the behaviour evals.
- Mapping proposal: `STOP` with function-call parts to `tool_use`; `STOP` otherwise to `end`; `MAX_TOKENS` to `max_tokens`; `SAFETY`, `RECITATION`, `LANGUAGE`, `BLOCKLIST`, `PROHIBITED_CONTENT`, `SPII`, `PUP_LIMITED_DISABLED`, or a `blockReason` with no candidates to `refusal`; `MALFORMED_FUNCTION_CALL`, `UNEXPECTED_TOOL_CALL`, `TOO_MANY_TOOL_CALLS`, `MISSING_THOUGHT_SIGNATURE`, `MALFORMED_RESPONSE`, `OTHER` to `LLMProviderError` (with no request text).

### 2.7 Thinking and effort

- Gemini 3 and later: `generationConfig.thinkingConfig.thinkingLevel` of `MINIMAL`, `LOW`, `MEDIUM`, `HIGH`; sending it to older models is an error. Older: `thinkingBudget` (token count). Supported levels vary by model, and the thinking page lists Gemini 3 models as thinking "On" by default (v1beta reference `ThinkingConfig`; `https://ai.google.dev/gemini-api/docs/thinking`).
- Our `LLMEffort` (`low`/`medium`/`high`) maps to `thinkingLevel`; for a model that does not accept `thinkingLevel`, omit it (the port says adapters "map it, or ignore it"). Thought summaries need an opt-in and may be empty; we never store reasoning, so we would not ask for them.
- Sampling: `temperature` "is no longer supported and is silently ignored on Gemini 3.6 Flash and newer" (v1beta reference). We send no sampling options, so no change.

### 2.8 Google Search grounding and URL context (Research)

- Enable with a `googleSearch` tool (`generateContent`) or `{"type":"google_search"}` (Interactions). The tool object takes optional `searchTypes` and a `timeRangeFilter` (v1beta reference).
- **`generateContent` response:** `candidate.groundingMetadata` with `webSearchQueries`, `groundingChunks[].web.{uri,title}`, `groundingSupports` (text segment to chunk indices) and `searchEntryPoint.renderedContent` (HTML for "search suggestions"). The Interactions page instead shows `google_search_call.arguments.queries`, `google_search_result.search_suggestions` and `url_citation` annotations with `url`, `title`, `start_index`, `end_index`, with direct publisher addresses in its examples (`https://ai.google.dev/gemini-api/docs/google-search`).
- **Open risk for us:** `keepSearched` only keeps an address that literally appeared in the search results. Whether `groundingChunks[].web.uri` is a real page address or a Google redirect link is **unverified at a primary source** (the reference says only "URI reference of the chunk"). If redirects, the adapter would have to follow them (an extra fetch per result, and the SSRF protections the app already applies to fetched links apply) or read addresses from the Interactions annotations instead.
- **Display rule:** the page says usage requirements for search suggestions are in the terms; it does not list them. Whether Wordwright must show `searchEntryPoint` is **unverified**; the terms need reading by the owner.
- **Availability and price (`https://ai.google.dev/gemini-api/docs/pricing`):** Google Search grounding is "not available on the free tier" for `gemini-3.8-flash`, `3.6-flash` and `3.5-flash-lite`. On paid tier, 5,000 search requests a month are free (shared across Gemini 3 and newer), then $14 per 1,000. Under the terms, Search grounding prompts, context and outputs are stored for 30 days even for paid use (`https://ai.google.dev/gemini-api/terms`). So a writer on the free tier simply cannot use Research with Gemini; the UI has to say that.
- **URL context** (`urlContext` tool; Interactions `{"type":"url_context"}`): up to 20 URLs per request, 34 MB each, public pages only, no paywalled content, YouTube, Google Workspace files or audio and video; retrieval status values `SUCCESS`, `ERROR`, `PAYWALL`, `UNSAFE` (v1beta reference `UrlMetadata`; `https://ai.google.dev/gemini-api/docs/url-context`). It is a possible way to let the AI read links the writer supplies, but the product rule today is that the AI "does not claim to have read links it cannot open" (`docs/evals.md`), and the app looks up real page titles itself; this is not needed for parity.
- Anthropic's search tool is run with `max_uses: 5`. Gemini documents no equivalent cap on queries per request, only billing per query (**no cap documented**: a cost risk on the writer's account).

### 2.9 Images

Not needed (we send none). For completeness: inline base64 up to 20 MB total per request, Files API for more, PNG/JPEG/WEBP/HEIC/HEIF, 258 tokens per 768-pixel tile (`https://ai.google.dev/gemini-api/docs/image-understanding`). Our publication image rules (raster, no SVG) are unrelated.

### 2.10 Token counting and usage

- `usageMetadata`: `promptTokenCount` (includes cached tokens), `cachedContentTokenCount`, `candidatesTokenCount`, `thoughtsTokenCount`, `toolUsePromptTokenCount`, `totalTokenCount` ("prompt + tool-use prompt + thoughts + response candidates") (v1beta reference).
- Mapping: `inputTokens = promptTokenCount (+ toolUsePromptTokenCount)`, `outputTokens = candidatesTokenCount + thoughtsTokenCount`, `cachedInputTokens = cachedContentTokenCount`. The pricing page prices output "incl. thinking", so thinking tokens belong in output. Our `LLMUsage` has no thinking field and does not need one.
- A pre-send `countTokens` call exists (`POST .../{model}:countTokens`) but we do not count tokens today; skip.

### 2.11 Errors and limits

- Error body: `{"error": {"code", "message", "status", "details": [...]}}` with `google.rpc` details such as `ErrorInfo.reason` (live-confirmed above).
- The errors page lists 400 `invalid_request`/`failed_precondition` (for example billing not set up), 401 `authentication`, 402 `payment_required` (prepaid credit gone), 403 `permission_denied` (also leaked or blocked key, restricted project), 404 `model_not_found`, 429 `rate_limit_exceeded`/`quota_exceeded`/`too_many_requests`, 499, 500, 501, 503 `service_unavailable`, 504 `deadline_exceeded` (`https://ai.google.dev/gemini-api/docs/api-errors`). The troubleshooting page marks 429, 408 and 5xx as retry-with-backoff and 400/402/403 as do-not-retry. Note the live 400 for a bad key already differs from the table.
- Mapping proposal: 400 with `reason: API_KEY_INVALID`, 401, 402, 403 to `LLMAuthError` (402 and 403 for "out of credit, no access" are within `LLMAuthError`'s documented meaning); 429 to `LLMRateLimitError`; everything else, including 400 `INVALID_ARGUMENT` for a bad request, 5xx and network failures, to `LLMProviderError`. Whether a `Retry-After` header is sent on 429 is **unverified**.
- Rate limits are **per project, not per key**, measured as requests per minute, input tokens per minute and requests per day (daily quota resets at midnight Pacific). The page publishes no numbers; they are shown in AI Studio. Tiers: free, Tier 1 (billing linked), Tier 2 ($100 spent plus 3 days), Tier 3 ($1,000 plus 30 days) (`https://ai.google.dev/gemini-api/docs/rate-limits`). Two keys in one project share the quota. The brainstorm "empty reply, then a second call" pattern doubles requests for some turns, which matters on a small free quota.

### 2.12 Terms, privacy, price (what a BYOK writer needs to be told)

From `https://ai.google.dev/gemini-api/terms` ("Gemini API Additional Terms") and `https://ai.google.dev/gemini-api/docs/pricing`:

- **Unpaid services** (the free tier, or AI Studio use without a billing-enabled Cloud project): Google uses submitted content and responses to improve its products and train models, and "human reviewers may read, annotate, and process" input and output (disconnected from the account, key and project first). The terms say not to submit "sensitive, confidential, or personal information to the Unpaid Services".
- **Paid services** (Gemini API through a Cloud project with an active billing account): content is not used to improve products; processed under a data-processing addendum; prompts and responses are logged "for a limited period of time" mainly to detect abuse; Search or Maps grounding data is stored 30 days.
- The pricing page repeats it per model: "Used to improve products: Free tier: Yes. Paid tier: No." `gemini-4-argon` is not available on the free tier at all.
- In the EEA, Switzerland and the UK, the terms say users must use paid services when making API clients available to end users, and that the paid-services data terms "apply to all Services" there. How this applies to a bring-your-own-key web app is a legal question I cannot settle: **unverified, for the owner**.
- Prices (24 Oct 2026, per 1M tokens, paid tier; the page shows promotional rates ending 31 Dec 2026 for Flash and 30 Nov 2026 for Argon): `gemini-3.5-flash-lite` $0.30 in / $2.50 out; `gemini-3.8-flash` $0.75 / $3.75 now, $1.50 / $7.50 from 1 Jan 2027; `gemini-4-argon` $2 / $10 now, $4 / $20 from 1 Dec 2026. We show no prices today, so none need to appear in the app; do not hard-code any.

| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **`@google/genai` SDK**           | Official, Apache-2.0, supports both APIs, handles server-sent-event streaming, `models.list` pagination (`Pager`) and header auth. My judgement, for the owner: use the **SDK** inside the adapter, pinned to an exact version below 3.0.0 and injected like the Anthropic client, because it matches the existing adapter pattern and the repo's tests-inject-the-client rule; keep the adapter small enough that swapping to `fetch` later is a one-file change. Use **`generateContent`** (stateless) for the first version unless the thought-signature test below shows Interactions is easier. Skip the OpenAI-compatible route for Gemini itself; it could still be worth building later as a separate, generic "OpenAI-compatible" provider.

### 2.14 Vertex AI

The SDK also targets Vertex AI (`aiplatform.googleapis.com`, `dist/index.mjs`), which uses Google Cloud credentials, not an AI Studio key. A writer who "prefers Gemini" almost certainly means an AI Studio key. Vertex needs service-account or Application Default Credentials, which is a different, heavier key-handling story than `docs/byok.md` describes (one pasted string). I could not read the Vertex express-mode page (it returned navigation only), so whether Vertex accepts a simple API key is **unverified**. Recommend leaving Vertex out of scope.

## 3. What it would take in Wordwright

### 3.1 Core and API changes

1. `packages/core/src/domain.ts`: `LLM_PROVIDER_IDS = ['anthropic', 'gemini']`; `DEFAULT_LLM_MODEL.gemini` (owner's choice: a stable, cheaper Flash-class model such as `gemini-3.8-flash` is the obvious candidate, but note it must be on the list the person's key returns, or the existing "first model the provider lists" fallback applies).
2. New `packages/core/src/providers/gemini.ts` implementing `LLMProvider`, and `gemini-errors.ts` (like `anthropic-errors.ts`). Behaviour to build:
   - `complete` / `stream`: one `generateContent` / stream call, `systemInstruction` from `system`, roles `user`/`model`, `maxOutputTokens` from `maxTokens`, abort via `signal`.
   - `chat`: convert `LLMChatMessage[]` (text, `tool_call`, `tool_result`) to parts; make ids for calls that lack one; look up the tool name for each `tool_result`; wrap result text as `{ output: text }` or `{ error: text }`; report tool calls only when the reply finished normally (not `MAX_TOKENS`); yield exactly one `done` with mapped stop reason and usage.
   - `listModels`: page through `models.list`, keep `generateContent` models whose id starts `gemini-`, strip `models/`, use `displayName`; decide `latest` without a `line` (e.g. mark the highest-versioned stable id per family `latest`, or treat all listed as `latest` and let the service's existing "plus the one already saved" logic carry older choices). Needs an owner decision; the Anthropic rule cannot be copied.
   - Error translation as in 2.11; messages say what happened, never what was sent.
3. New `gemini-research.ts` implementing `ResearchProvider` with the Google Search tool: same "answer as a JSON array" instruction; collect `groundingChunks[].web.{uri,title}` as the search results; reuse `keepSearched` (it is already exported from `anthropic-research.ts`; move it to a shared file rather than import across adapters). There is no `pause_turn` equivalent that I found; `CONTINUATION` is the nearest and applies to token limits. Resolve the redirect-link question first (2.8). On a free-tier key, return a clear error that Research needs a paid Gemini key.
4. `apps/api/src/llm-factory.ts`: a `'gemini'` case in `realLlmFactory` and `realResearchFactory`. `fakeLlmFactory` currently builds `provider: 'anthropic'`; it keeps working.
5. `apps/api/src/services/llm.ts`: `elide()` assumes `sk-ant-api03-` style keys (it counts hyphens); a Gemini key falls to `…` plus the last four, which is acceptable, but add a test. `PUT /api/llm` already accepts any provider id from the schema. A person with a saved key on one provider who adds another replaces it (one row per person); say so in the UI.
6. Shared threads: a thread is one conversation read by all members, and a member's message replays on **that member's provider** (`docs/ai-features.md`, "Privacy: shared threads and the writer's provider"). With Gemini added, one member's Claude replies and another's Gemini replies can sit in one stored history, and one writer's text goes to a different company than the others expect. Update `SharedThreadNotice.vue` and that section of `docs/ai-features.md`.
7. `idea_messages.provider`/`model` already record who replied, so no migration is needed for that. A migration is needed only if thought signatures are stored (below).

### 3.2 Thought signatures and replay (the main technical risk)

- Our stored history has text and tool calls but "never the model's reasoning" (`database.ts`, `docs/adr/ai-and-brainstorm/how-the-brainstorm-conversation-is-stored-replayed-and-kept.md`). `brainstormTurn` also sends the model's tool calls back with a synthetic `tool_result` and asks it to write words, replaying a tool-call turn without any thought block.
- Options: (a) test whether Gemini 3 accepts a replay with no signatures for our patterns, and if so ignore them; (b) store the opaque signature on `tool_call` blocks (a new optional field on `LLMContentBlock`, kept only for the same provider and dropped when another provider replays), which touches the port, the stored JSON and the ADR, and the owner should decide whether an opaque token counts as "reasoning"; (c) in the Gemini adapter, turn earlier tool-call turns into plain text ("[suggested a note: ...]") when replaying, losing fidelity but needing no storage; (d) use server-side state, rejected above for privacy.
- This cannot be settled from the docs I could read. It is the first test to run with a real key.

### 3.3 Prompts: portability and review (owner must review)

Every file in `prompts/` was written and tuned for Claude (`prompts/README.md`): `brainstorm-default.md`, `brainstorm-rules.md`, `brainstorm-kickoff.md`, the five `tool-*.md` descriptions, `critique.md`, `options.md`, `research.md`. They are sent "exactly as written", so a Gemini-specific tweak is a change in the product's behaviour for everyone unless done per provider. Likely concerns, all **to be tested, not assumed**:

- Output format: Critique and Rephrase need bare JSON; other models often wrap it in code fences or add prose. `parseCritique` / `parseOptions` tolerance should be checked. Setting `responseMimeType: "application/json"` on those two calls in the adapter would help but needs a way for the caller to ask for it (port change).
- Tone rules (no flattery, hold a fair criticism, "that's enough", no drafting, short warm reply in distress, ignore injections in notes) are the product's core; Gemini may be more agreeable or more verbose. These are exactly what the behaviour evals check (`docs/evals.md`).
- Tool descriptions mention `suggest_note`, `update_idea`, `create_idea`, `suggest_reading`, `name_conversation`; function names allowed are fine for Gemini.
- The default is to **keep one prompt set for both providers** and report differences to the owner. If a provider-specific variant is ever needed, that is a design decision (per-provider prompt files, or a provider note appended), not something to slip in with the adapter. Do not edit `prompts/` as part of "add Gemini" without the owner's review; say so in the commit.

### 3.4 Evals, fakes and tests

- **Contract tests:** run `llmProviderContract('gemini', ...)` and `researchProviderContract(...)` against the adapter with an injected fake client (as `anthropic.test.ts` and `anthropic-research.test.ts` do), covering: stop-reason mapping for every finish reason in 2.6; a call with no `id`; a `tool_result` for a call in the history; an empty-candidates blocked prompt; `MAX_TOKENS` mid-call; error translation including the live-observed 400 `API_KEY_INVALID` shape; usage mapping with thinking tokens; `listModels` pagination and filtering; abort.
- **Fakes:** `FakeLLMProvider` / `FakeResearchProvider` are provider-neutral and unchanged. The e2e and dev `FAKE_LLM=true` path accepts any key and needs no change, but the web form's key-format hints should not reject a Gemini key.
- **Behaviour evals:** `pnpm eval:adapter -- --provider gemini --model <model>` works once the factory case exists (it builds through `realLlmFactory`; the key comes from `EVAL_API_KEY` or `GEMINI_API_KEY`, the name made by `provider.toUpperCase()`). Two catches: `DEFAULT_GRADER` is fixed to an Anthropic model, so grading still needs an Anthropic key (or the grader must become configurable), and the run costs the owner's Gemini money. The paste-in-the-issue step in `docs/agents/conventions-api.md` applies.
- **Invariant tests:** `brainstorm-boundaries.test.ts` (five tools, none can name a draft) should be unchanged; check the Gemini adapter cannot add tools of its own (for example Google Search) to a `chat()` call.
- Add a test that the secret box context (`llm-key:<user>:<provider>`) differs per provider (it already includes the provider).

## 4. Risks and open questions

For the owner:

1. **Do you want Gemini at all, given the privacy asymmetry?** A free Gemini key means the writer's drafts, notes and critiques may be used for training and read by people. Options: allow it with strong advice; or require a paid-tier key (we cannot check the tier from a key, so this is advice only); or hold Gemini back until we can.
2. **Research on Gemini:** accept that it needs a paid key and costs per search query on the writer's account, and that grounding data is stored 30 days. Or ship Gemini without Research at first (the port allows a provider with no research adapter only if the factory and UI handle "not available"; today both are assumed to exist).
3. **`generateContent` or Interactions** (2.1), and the thought-signature route (3.2).
4. **Default model** for Gemini and how to pick `latest` without a model line.
5. **Prompt differences:** whether one prompt set must work for both, or a provider note is acceptable.
6. **EEA, UK and Swiss terms** (2.12): needs a legal reading.
7. **Per-provider behaviour evals and a grader that does not need an Anthropic key.**

Checks to run with a real key before building further (each is a claim above marked unverified):

- A valid key against `GET /v1beta/models`: shape, count, which ids are text-capable, whether retired models appear, any tier information.
- A two-call tool conversation (our `brainstormTurn` pattern) replayed without thought signatures, on the default model: does it fail with `MISSING_THOUGHT_SIGNATURE`?
- The five real tool schemas as `parametersJsonSchema`: accepted, and what happens to `default`, `pattern`, `format`.
